# Region main+0x1000000 to main+0x13fffff (0x7001000000-0x70013fffff)

Scope: 16 windows of 256 KB, about 4 MB, module `main`. Index-based notes only. Tags: [C] confirmed by a string, SDK
symbol or documented fact; [I] inferred from a strong pattern; [H] guess. Generated C was read only for vtable
structure and string-bearing handlers; most of the lifted code was not read.

## Summary

This 4 MB stretch of the game is where most of the "match flow" logic lives. The game's top-level state machine
(one class per screen or phase of a game: pre-play, batter up, in play, play over, inning over, game over, and so on)
has its handlers here, and each state's log strings name its sub-states. Around it sit the play-by-play and crowd audio
cues, the stats and presentation screens, the stadium lighting manager, the Home Run Derby state machine, the save and
batter-streaming code, the animation core, and a few third-party libraries (libwebp image codec, mini-XML parser)
compiled in. A strong, checkable finding: the BATTER_UP slot-5 handler contains a state log line for every sub-state
of batting, so its strings alone reproduce the pitch sequence. The lighting and stadium pieces are the likeliest place
for the stadium-bake stalls already documented elsewhere, but only the function names were checked here.

- The 12 states and their handler addresses were taken from `vtables.jsonl`; the slot numbers are list positions [C].
